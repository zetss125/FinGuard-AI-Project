# FinGuard AI Backend Explanation

## Overview

This document explains how the FinGuard AI backend works, with a special focus on fraud detection, authentication, and the technologies used.

The backend is a Python web API built with FastAPI. It stores data in SQLite and uses a simple combination of rule-based logic and transaction scoring to identify suspicious activity.

## Technologies Used

* Python 3.13
* FastAPI for the web API
* Uvicorn as the ASGI server
* SQLite for the local database
* Pydantic for request validation and response models
* HTTP Bearer authentication for secure access
* Built-in Python modules: `sqlite3`, `uuid`, `hashlib`, `datetime`

## System Architecture

The backend is organized into several layers:

1. **API Layer**
   * Receives HTTP requests from the frontend or API client.
   * Defines endpoints such as `/register`, `/login`, `/transactions`, `/credit`, `/dashboard`, and `/alerts`.

2. **Authentication Layer**
   * Uses bearer token authentication.
   * After login, the system returns a token.
   * Protected endpoints require `Authorization: Bearer <token>`.

3. **Business Logic Layer**
   * Handles user registration, login, transaction processing, and credit advice.
   * Calls the fraud scoring and credit recommendation functions.

4. **Data Layer**
   * Stores users, sessions, transactions, and alerts in SQLite.
   * Uses simple SQL operations for reading and writing data.

## User and Session Flow

### Registration

1. The user submits `username`, `password`, `income`, `expenses`, and `savings` to `/register`.
2. The backend hashes the password with SHA-256.
3. User data is saved in the `users` table.

### Login

1. The user sends `username` and `password` to `/login`.
2. The backend verifies the password hash.
3. If valid, it creates a session token in the `sessions` table.
4. The token is returned to the client.

### Protected Requests

1. The client sends the token with requests to protected endpoints.
2. The backend checks the token in the `sessions` table.
3. If the token is valid, the backend loads the associated user and continues processing.

## Fraud Detection Process

Fraud detection in FinGuard AI is done using a simple scoring algorithm based on transaction size and user financial behavior.

### How the score is calculated

The backend applies these rules when a transaction is submitted:

* Start with a base fraud score of `10`.
* Add `30` points if the transaction amount is at least `1000`.
* Add `20` points if the transaction amount is more than 30% of the user’s income.
* Add `20` points if the transaction amount is more than 90% of the user’s expenses.
* Add `15` points if the transaction location is not one of the trusted values: `home`, `office`, or `local`.

The score is capped at `100`.

### Risk levels

The final fraud score is converted into a risk label:

* `0-34` → `low`
* `35-59` → `medium`
* `60-100` → `high`

### Alerts

If a transaction is classified as `medium` or `high`, the backend automatically adds an alert to the `alerts` table. This helps the user understand why the transaction was flagged.

## Credit Recommendation

Credit advice is calculated using the user’s income, expenses, and savings.

### Rule-based recommendations

* If the expense ratio (`expenses / income`) is greater than `0.7`, credit risk becomes `high` and the system recommends reducing expenses.
* If the savings ratio (`savings / income`) is less than `0.15`, the system returns `medium` risk and recommends building savings.
* Otherwise, the system returns `low` risk and indicates the user is stable for a small loan.

## Dashboard and Alerts

The `/dashboard` endpoint returns:

* username
* income
* expenses
* savings
* credit recommendation
* credit risk
* recent alerts

The `/alerts` endpoint returns the recent alert messages generated by the backend.

## Why It Works

This backend is designed for a student-level financial app:

* It validates all inputs with Pydantic.
* It protects sensitive endpoints with bearer token authentication.
* It stores state in a simple SQLite database.
* It detects suspicious transactions using clear, explainable rules.

## Example Backend Flow

1. User registers with `/register`.
2. User logs in with `/login`.
3. Client stores returned token.
4. User submits a transaction to `/transactions` using the token.
5. Backend evaluates the transaction and stores it.
6. If the transaction is suspicious, the backend creates an alert.
7. User views summary data at `/dashboard`.

## Notes

* This backend does not use a full machine learning model. It uses a rule-based scoring approach that is easy to understand and explain.
* The fraud detection approach is intentionally simple for a college project, but it can be extended with real ML models in the future.
* `HTTPBearer` is used so swagger and other clients can pass the token in a standard way.
